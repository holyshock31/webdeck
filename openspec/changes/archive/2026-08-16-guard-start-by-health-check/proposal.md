## Why

「启动」的语义应该是「确保服务在跑」，但现状的自动启动（切换到该应用时）与手动启动（▶）都只按运行状态（stopped / error / unknown）决定是否拉起进程，不做健康探测。若服务已在外部启动（如用户在终端手动 `pnpm dsh`），WebDeck 启动时首次健康探测可能尚未返回、状态还是 unknown，会误判并 spawn 一个重复实例：新实例绑定同一端口失败后退出，状态短暂闪红再被健康检查拉回 running——白拉一次进程。用户明确要求：健康检查通过时不应再拉起应用实例。

## What Changes

- `src/main/monitor.js`：新增 `isHealthy(app)` 启动前守卫——用应用的监测配置（检查 URL / 期望状态码 / 探测超时）做一次即时探测，通过返回 true；监测未启用时返回 false（维持按状态启动的原行为）
- `src/main/index.js` 两处拉起入口先过守卫：
  - 切换标签自动启动（activateApp）：健康通过 → 不 spawn，直接标记 running「健康检查通过，服务已在运行」；不通过 → 照常拉起
  - 手动启动（app:start）：健康通过 → 返回 `{ ok, skipped: true }` 不 spawn；不通过 → 照常拉起
- 行为边界：停止（⏹）与退出清理（stopOnQuit）语义不变，只作用于 WebDeck 自己拉起的进程；无新增持久化字段、无新增状态
- 注：代码与测试已随本提案落地并验证（单测测试 8 四类断言；冒烟第 8 步 `skipped=true spawned=false status=running`），本提案记录该行为变更并冻结规格增量
- 范围：新增能力（行为修正）；验收方式为手动验证 + 自动化测试

## Impact

- **运行状态**：状态机（starting / running / error / stopped）不变；健康通过时手动启动变为无害 no-op，状态直接置 running，按钮随即显示 ⏹
- **性能**：每次拉起前多一次本地探测（复用监测超时，默认 3s；本地服务通常毫秒级返回）
- **兼容性**：对「服务未运行」场景行为与现状完全一致（探测失败 → 照常拉起）；仅改变「服务已在运行」场景——不再重复拉起
- **持久化**：无 schema 变化，webdeck.json 读写与旧版本完全兼容
- **风险**：低；启动瞬间的 unknown 竞态被守卫兜住，重复实例问题消除
